# 13_台式机三维仿真与 VLA 验证方案

## 1. 当前问题与结论

当前抓取链路已经能够完成：

- 相机取图
- VLM / 规则定位目标
- 手眼标定后输出目标点

但在进入机械臂执行阶段后，仍然会出现：

- 已经拿到目标坐标，但 `move_above` / `grasp` 失败
- 机械臂报 `no_ik_solution`
- 同一个目标点在不同姿态或不同预抓取高度下，可达性差异很大

这说明当前瓶颈已经不只是“看得准不准”，而是：

1. `目标点 -> 接近姿态 -> 预抓取位 -> 轨迹` 这条链路没有被系统验证
2. 仅依赖示教器或手动拖动机械臂，能找到个别可行姿态，但不能稳定解释为什么可行或不可行
3. 在真机上反复试错，成本高且有安全风险

因此当前阶段的明确结论是：

- 后续验证主场应切换到你的台式机
- 用三维仿真先验证 `目标点是否可达`、`接近姿态是否合理`、`轨迹是否避碰`
- 再把仿真里筛选出的可执行方案下发到真机

## 2. 总体原则

### 2.1 计算边界

台式机负责重计算：

- 三维仿真
- 轨迹搜索
- IK / 碰撞检测
- VLA / VLM 推理
- 离线日志回放与批量评估

树莓派只负责边缘执行：

- 相机采集
- SDK 调用
- CAN 通信
- 夹爪控制
- 力传感器与接触检测

不要把 VLA / VLM 推理默认放到 Raspberry Pi 上。

### 2.2 模型边界

第一阶段不要让 VLA 直接输出关节轨迹。

更稳妥的分层是：

- `VLM / VLA`：输出动作意图、候选抓取策略、候选接近方向
- `规划器`：负责 IK、碰撞检测、轨迹生成和候选打分
- `真机执行层`：执行已经被仿真验证过的动作

也就是说，VLA 在第一阶段更像“策略选择器”，不是“直接开机械臂的轨迹控制器”。

## 3. 推荐架构

```text
真实相机 / 历史日志
        |
        v
台式机回放与数字孪生
        |
        +--> VLM / VLA 给出目标与候选策略
        |
        +--> 运动规划器批量验证:
             - 多组 rpy 候选
             - 多组 standoff 候选
             - IK 求解
             - 自碰撞 / 环境碰撞
             - 轨迹评分
        |
        v
输出最优可执行 plan
        |
        v
Pi / robot_server 执行
        |
        v
真机状态与结果回传
```

## 4. 与当前仓库的衔接方式

当前仓库已经有可以直接复用的三段能力：

1. `calibration/scripts/pick_place_client.py`
   - 已具备扫描、目标定位、调试图输出、结果落盘能力
2. `calibration/scripts/robot_server.py`
   - 已具备执行侧 HTTP 动作接口
3. `nero/kinematics.py`
   - 已具备离线 FK 预览能力，可作为桌面仿真的基础校验模块

下一步不建议继续把所有逻辑都塞进 `pick_place_client.py`。

更合理的做法是在台式机侧新增一个“仿真验证层”，放在感知和真机执行之间：

```text
pick_place_client.py
    -> 输出目标点 / 调试日志
desktop_sim_validator
    -> 判断是否可达、是否避碰、是否需要换姿态
robot_server.py
    -> 只执行通过验证的 plan
```

## 5. 推荐技术栈

### 5.1 台式机环境

建议台式机作为主开发环境，最低建议：

- `RTX 4080 Super`
- `32 GB` 以上内存，优先 `64 GB`
- `200 GB` 以上可用 SSD 空间用于环境、模型和数据缓存

操作系统建议两种形态二选一：

- 方案 A：`Windows + WSL2 Ubuntu`
  - 适合继续沿用现有 Windows 桌面环境
  - Python、模型推理、数据处理优先放在 WSL2
- 方案 B：独立 `Ubuntu 22.04 / 24.04`
  - 适合后续长期做训练、仿真和部署

如果你当前桌面主要是 Windows，第一阶段建议优先走方案 A。

### 5.2 仿真与规划

- 仿真：`ManiSkill3 + SAPIEN`
- 运动学 / IK：`pytorch_kinematics` + 当前 `NERO` DH 参数
- 轨迹规划：`mplib / OMPL` 一类采样规划器
- 碰撞模型：先用简化碰撞体，不追求一开始就做高保真网格

### 5.3 模型侧

第一阶段建议分成两类模型：

- `VLM`：负责识别、语义解释、候选抓取区域判断
  - 可继续复用当前已验证的视觉模型链路
- `VLA`：负责候选动作排序或策略选择
  - 首选轻量路线，如 `SmolVLA` 或 `ACT` 风格策略模型

不建议在第一周就把 `OpenVLA` 或“大模型直接输出关节轨迹”作为主线目标。

## 6. 分阶段实施

### Phase 0：台式机环境准备（0.5-1 天）

目标：

- GPU 驱动、CUDA、Python 环境可用
- ManiSkill3 / SAPIEN 能跑最小样例
- 能在台式机读取当前项目里的调试图和日志

交付物：

- 可复现的桌面环境
- 一份安装记录

### Phase 1：失败 case 离线回放（2-3 天）

目标：

- 把当前真机失败 case 导入仿真
- 复现“目标点已知但轨迹不可解”的现象
- 先做失败归因，不急着上 VLA

重点输出：

- `reachability_report.md`
- `reachability_report.json`

需要归类的原因至少包括：

- 超出工作空间
- 当前 `rpy` 不可解
- `standoff` 设置不合理
- 存在环境碰撞或自碰撞
- 手眼误差导致目标点偏移到不可达区域

### Phase 2：候选姿态搜索与轨迹评分（4-5 天）

目标：

- 不再只试单一模板姿态
- 围绕当前抓取模板采样多组 `rpy`
- 同时采样多组 `standoff`
- 批量做 IK、碰撞检测和轨迹评分

输出应包括：

- 每个目标点的可达候选数
- Top-K 可执行方案
- 推荐执行姿态与接近方向

这一阶段的核心不是“抓得快”，而是“先找出稳定能解的姿态分布”。

### Phase 3：VLA 接入仿真验证（4-5 天）

目标：

- 让 VLA 参与候选排序和失败恢复策略
- 验证 VLA 是否能在仿真里做出比固定模板更好的选择

第一阶段 VLA 只负责：

- 候选抓取姿态排序
- 选择接近方向
- 判断失败后应重拍、重抓还是换姿态

第一阶段 VLA 不负责：

- 直接输出整条关节轨迹
- 替代规划器做避碰
- 替代边缘控制器做实时控制

### Phase 4：仿真结果回灌真机（3-4 天）

目标：

- 将仿真里通过验证的 plan 回灌到真机
- 比较“仿真筛选前后”的真机成功率差异

建议对比指标：

- `no_ik_solution` 发生频率
- `move_above -> grasp` 成功率
- 平均重试次数
- 单次节拍变化

## 7. 建议新增的软件模块

建议在台式机侧新增独立目录，而不是继续把逻辑堆到现有脚本中：

```text
sim/
  replay_case.py           # 回放真机 case
  build_scene.py           # 构建简化场景
  search_grasp_pose.py     # 多姿态 / 多 standoff 搜索
  plan_trajectory.py       # 轨迹规划与碰撞检测
  score_candidates.py      # 候选打分
  export_plan.py           # 导出给 robot_server 的 plan
  vla_policy_runner.py     # 调用 VLA 做候选排序
```

建议数据输入输出格式统一为 JSON，至少包含：

- `target_xyz`
- `seed_uv`
- `camera_pose`
- `tool_rpy_candidates`
- `standoff_candidates_mm`
- `best_plan`
- `failure_reason`

## 8. 第一阶段不做什么

为了尽快落地，第一阶段明确不做以下内容：

- 不在树莓派上做模型推理
- 不让 VLA 直接生成低层关节轨迹
- 不把示教轨迹当成主方案
- 不先追求高保真透明材质仿真
- 不一开始就做力控压入的完整接触仿真

第一阶段只解决一个核心问题：

`相机确认坐标之后，为什么真机到不了，以及如何在下发前先把可执行轨迹筛出来。`

## 9. 建议的近期目标

如果按当前资源推进，建议把台式机阶段的近期目标设为：

1. 用当前抓取日志复现 3 个失败 case
2. 对每个 case 找到至少 1 组稳定可执行的 `rpy + standoff`
3. 让仿真输出一份可直接下发给真机的 plan
4. 用真机验证“仿真筛选后”的成功率是否显著提升

只要这四件事做成，就说明这条“台式机仿真先行、VLA 参与策略选择、Pi 负责边缘执行”的路线是正确的。
