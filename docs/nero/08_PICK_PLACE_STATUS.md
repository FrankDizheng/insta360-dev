# 白瓶抓放现状（2026-03-30）

## 1. 当前结论

- 当前场景下，"白色瓶子抓起并放到蓝色区域" 已经成功跑通。
- 本轮耗时偏大的主因不在推理，当前 `step1 -> step4` 链路没有走 VLM 决策；瓶颈主要在相机采集、重复建连、人工选点和运动参数试探。
- 树莓派仍应只负责 SDK / 相机 / CAN / 执行，推理应放在本地或独立算力机。

## 2. 本轮成功参数

- 固定扫描位：`SCAN_POSE_DEG = [-19.4, 10.7, 4.6, 63.0, 7.1, 1.4, 56.6]`
- Step 1 像素点：
  - `bottle: 260:360`
  - `blue_board: 810:400`
- Step 2：`standoff-mm 80`
- Step 3：`grasp-z-mm 330`，`lift-z-mm 400`
- Step 4：`place-z-mm 295`，`z-safe-mm 400`

## 3. 为什么整条流程仍然慢

### 3.1 Step 1 采集本身就偏慢

- 非常驻模式下，RGB-D 每次都要重新 `start/stop` Orbbec pipeline。
- 当前采集实现包含 `2.0s` settle 和 `15` 帧 warmup，因此单次扫描天然就是秒级开销。
- 如果像素点第一次选得不好，或者某个像素没有有效深度，就会触发重复扫描。

### 3.2 仍然是"跨脚本"流程，不是"单进程"流程

- 虽然 `step1~step4` 都已经支持各自的 `--persistent` 模式，但这只是"单脚本内部常驻"。
- 当前完整流程仍然按 `step1 -> step2 -> step3 -> step4` 分进程执行，所以机器人连接、TCP 设置、夹爪初始化会跨步骤重复发生。
- 这意味着已经减少了单步内的重复建连，但还没有消除跨步骤的重复建连成本。

### 3.3 Step 2 存在"接近到位但判定失败"的问题

- 本轮 `step2` 在目标上方 `80 mm` 的悬停位，实际已经接近目标。
- 但 `wait_move_done()` 的位置容差过严，导致脚本报超时。
- 现场读到的实际结果是：TCP 距瓶子 `XY ≈ 10.4 mm`，`Z ≈ 80.2 mm`，说明这是"接近成功但被判失败"，而不是完全没走到。
- 这种假失败会拖慢整条链路，因为人会额外检查状态、补做微调、重新下发下一步。

### 3.4 Step 3 的抓取高度对可达性很敏感

- 本轮 `grasp-z-mm 300` 会直接报 `NO_SOLUTION`。
- 把抓取高度提高到 `330 mm` 后，抓取立即成功。
- 说明当前瓶子位置、姿态和 TCP 组合下，抓取 Z 仍然需要试探，无法一次就稳定命中。

### 3.5 人工选点仍在主链路里

- 当前 `step1` 仍依赖人工确认 `pixel-coords`。
- 这本身就会让流程受人机交互速度影响，不可能做到快速闭环。

## 4. 这轮现场结论

- 当前系统不是"不能做"，而是"能做但调参成本高、节拍慢"。
- 现在最优先的问题已经不是手眼/TCP 本身，而是流程编排和执行判定。

## 5. 下一步最值得做的优化

- 做一个真正的单进程 `pick_place_session.py`，把 `scan / move_above / grasp / place` 放进一个常驻会话里，彻底消除跨步骤重复建连。
- 放宽 `step2` 的完成判定，避免"几乎到位却报失败"。
- 给 `step3` 增加抓取高度回退链路，例如 `300 -> 315 -> 330`，减少人工试探。
- 尽量把像素点确认改成"一次拍照，多次复用"，避免为了修坐标重复采图。
